# Fix spec — agentic e2e run 260713-222807

**Status:** partially implemented; retained for outstanding WS1 and WS6 work · **Date:** 2026-07-13
**Source:** `daski-test/runs/260713-222807/` (`report.md`, `recommendations.md`)
**Repos touched:** daski-gateway (primary), daski-provider, daski-test

## 1. Background

The 2026-07-13 agentic e2e run (testnet, sandbox gateway) scored **1 pass /
5 fail** across six scenarios. Four of the five failures share a single
gateway-side root cause (the intent-search embedding model could not be
loaded, and the failure was neither contained nor communicated); the fifth
partially completed but failed a deliverable check. Total blast radius: zero
purchases in scenarios a, b, e2, e3 despite funded wallets and fully-specified,
principal-approved tasks.

This spec turns the run's findings into six workstreams. WS1 is the outage;
WS2–WS4 are the agent-UX defects that amplified it or surfaced alongside it;
WS5–WS6 are documentation and observability follow-ups.

## 3. Workstreams

### WS1 — Search resilience (P0, daski-gateway)

The outage fix, in three independent layers. Layer (c) alone would have
turned all four hard failures into passes.

**a. Remove the runtime network dependency (RC1).**
Prefetch the model at Docker build time (builder stage runs a small script
that instantiates the pipeline once, populating the transformers cache under
`node_modules/@xenova/transformers/.cache/`, which the runtime stage already
copies). Configure the embedder for local-only resolution
(`env.allowRemoteModels = false`) so production never contacts huggingface.co.
A build-time fetch failure fails the build loudly — the previous image keeps
serving. If build-time fetches also prove unreliable (HF throttling
anonymous cloud egress is the suspected cause of the 403), fall back to
vendoring the model files (~25 MB quantized + tokenizer) via git-lfs or
object storage.

**b. Never cache a rejection; warm up at boot (RC2, RC4).**
- On pipeline-load failure, clear `pipelinePromise` so the next call retries
  (with a short backoff/circuit-breaker so a hard outage doesn't add latency
  to every search).
- Kick off a non-blocking warmup embed at startup so a broken model surfaces
  in deploy logs, not in the first user-facing search.
- Surface embedder state in `/health` (e.g. `embedder: ok | degraded(<reason>)
  | disabled`) so daski-test preflight and Railway alerts catch degradation
  before scenarios run.

**c. Degrade instead of erroring (RC3; recommendations 1–2).**
Wrap the intent path (`syncSkillEmbeddings` + `embed`) in failure
containment. On any embedder failure, return a **successful** tool result:
the category/maxPrice-filtered catalog (the same shape the existing
`embedder: null` branch returns), plus machine-readable degradation markers:

```jsonc
{
  "providers": [ /* filtered catalog, unranked */ ],
  "ranking": "unavailable",           // vs "vector" on the happy path
  "warning": "intent ranking is temporarily unavailable; results are the full
              catalog filtered by category/maxPrice. Category-only calls do
              not use the ranking model.",
  ...
}
```
Optionally add a trivial lexical scorer (token overlap against the same
source text the embeddings index) — nice-to-have at the current catalog
scale (one provider), not required.

The raw upstream error string must never reach an agent. If even catalog
mode fails, return the actionable copy from recommendation 2
(`search_ranking_unavailable`, naming the category-only fallback) instead of
the transport error.

**Acceptance**
- With the embedder forcibly broken (test seam / env flag), every
  `daski_search_services` call still returns providers; scenarios a, b, e2,
  e3 complete discovery and reach payment.
- One failed load no longer poisons subsequent calls (unit test: throwing
  embedder → later stub embedder succeeds).
- `/health` reflects embedder degradation; daski-test preflight asserts it.
- Production image starts and serves intent search with outbound HF traffic
  blocked.

### WS2 — Category discoverability (P1, daski-gateway)

- **Ship the alias fix**: `9789e06` is code-complete on develop; it reaches
  the sandbox only via the next develop → main release. Call this out in the
  release notes; the e2e ran against v0.5.0 without it.
- **Extend the alias table** (`src/discovery/format.ts`): add
  `entity-formation` and `incorporation` → `legal`. Rationale: search
  results themselves display `serviceSlug: "entity-formation"`, so agents
  will keep guessing it (they did, in e1 and e4, burning 3–5 calls each).
- **Hint on empty results**: when a search returns zero providers (both
  catalog and intent modes), include `availableCategories` — the distinct
  canonical buckets currently in the cache — so an agent's wrong guess
  self-corrects in one turn instead of a brute-force loop. (Intent mode
  already has `nearMisses`; this is the catalog-mode equivalent.)
- **Document the taxonomy** where agents read it (recommendations 1, 3):
  - `daski_search_services` description: intent ranking uses an embedding
    model; category-only calls bypass it; list the canonical buckets and
    note aliases are accepted.
  - SKILL.md: a category cheat-sheet near the search steps (entity/LLC
    formation → `business-formation`/`legal`; domains/DNS/hosting →
    `infrastructure`; etc.), plus "when intent search is unavailable, list a
    category with a bare `{ category }` call".

**Acceptance:** `{category:'entity-formation'}` returns the formation
provider; an empty result carries `availableCategories`; e1/e4-style slug
guessing disappears from the next run's transcripts.

### WS3 — Paid-path signed retry (P1, daski-gateway)

- **Auto-fill from the gateway's own records (RC6).** On a signed retry
  (`envelopeAuth` present) for a skill the catalog marks `paymentRequired`,
  when `serviceRef`/`transactionHash` are omitted, look up the settled
  challenge by `paymentId` (the envelope binds it) and inject them. The
  gateway settled the payment; it is the authority on those values.
- **Fail fast when it can't.** If lookup fails or conflicts (paymentId not
  settled, belongs to a different buyer/skill), reject **before forwarding
  to the provider** with an error naming the exact missing/mismatched
  fields. Rejecting pre-forward means the single-use envelope is not
  consumed — the agent can retry with the same signature instead of
  re-running the whole handshake.
- **Rewrite the tool description** (recommendation 4) to the positive rule:
  "second call = first call's exact args + `envelopeAuth` + `messageId`,
  nothing removed." Keep it — direct-A2A callers don't get the auto-fill.

**Acceptance:** replaying e4's mistake (drop both fields on the signed
retry) succeeds with zero extra roundtrips; a genuinely inconsistent retry
fails at the gateway with field-level guidance and an unconsumed envelope.

### WS4 — Deliverable artifacts an agent can actually deliver (P1, gateway + provider + daski-test)

The provider's document-URL security model (one-time, short-TTL,
audience-bound, capability-gated — RC7) is sound and stays. What's missing
is a legitimate retrieval path and honest metadata.

- **Gateway: new tool `daski_fetch_artifact`.** Executes the documented
  handshake on the agent's behalf: GET the artifact URL → receive the
  audience challenge → return the EIP-712 typed-data for the wallet (same
  two-call pattern as every other gateway tool) → signed retry with the
  `X-Daski-Task-Capability` header → return the document (base64 blob /
  MCP resource, size-capped) plus content-type verification. This is the
  only way an agent can hand its principal an actual PDF rather than a
  link that dies in 15 minutes. Exact response encoding and size cap are a
  design-time decision.
- **Provider: honest artifact metadata.** Extend the artifact `data` block
  with explicit access semantics, e.g.
  `access: { oneTime: true, expiresAt, protocol: "daski-doc-download/1" }`,
  so neither agents nor harnesses read `mimeType: application/pdf` as
  "public URL serving a PDF". (The prose message already explains the
  handshake; structured fields make it machine-checkable.)
- **SKILL.md: artifact-delivery guidance** (recommendation 5, adapted to the
  real design): when the principal asked for durable proof, retrieve the
  bytes via the handshake and deliver them — or hand over the stable
  identifiers (entity handle + document ID) **together with** the statement
  that a fresh link can be minted on demand via `download-entity-document`.
  Never present a one-time short-TTL URL as "proof you can keep", and never
  claim delivery without verifying retrieval works.
- **daski-test: fix the deterministic check.** "formation document serves
  PDF" must perform the capability handshake (or call the new gateway tool)
  instead of a bare GET, which this design intentionally rejects.

**Acceptance:** e1's document check passes end-to-end; the principal-visible
transcript contains either an attached/delivered PDF or accurate re-mint
instructions — no dead links described as permanent.

### WS5 — SKILL.md upfront-collection & blocked-state discipline (P2, daski-gateway)

- **Per-member email** (recommendation 6): in the form-entity upfront
  template, ask whether each member has their own filing-correspondence
  email or whether the company contact email should be reused — kills the
  e2 mid-flow roundtrip.
- **Blocked ≠ complete:** add an explicit rule: if the marketplace or a
  required tool is down and the purchase cannot proceed, report the task to
  the principal as **blocked** and stop — do not wrap up claiming you'll
  "keep retrying in the background" (there is no background after the
  session ends). e2's session self-reported complete with nothing filed.

### WS6 — Observability & harness hygiene (P2, daski-provider + daski-gateway + daski-test)

- **Provider:** include `taskId` (and `skillId`, `paymentId`, JSON-RPC
  method + outcome where resolved) in the A2A request-completed log line so
  run artifacts correlate. Keep payloads out — the log sanitizer's redaction
  posture is unchanged; these are opaque identifiers.
- **Gateway:** log one structured line per MCP tool call (tool name,
  ok/error, duration, correlation id). Today `/mcp` traffic is
  indistinguishable `POST /mcp` entries, which is why a search outage left
  no gateway-side trace the harness could point at.
- **daski-test:** investigate the provider-DB connection dropping mid-run
  (e2/e3 report "provider DB not reachable this run" while preflight and
  e1/e4 used it fine) — reconnect rather than skip checks.

## 4. Rollout order

1. WS1 (b) + (c) — small, self-contained gateway changes; unit-testable with
   the existing stub-embedder seam. Ship first: they defuse the outage class
   regardless of upstream cause.
2. WS1 (a) — Dockerfile/build change; verify image size + offline start.
3. WS2 + WS3 + WS5 — gateway code/docs; WS2's alias entries ride along.
4. WS6 — provider + gateway log lines.
5. WS4 — needs a short design pass (binary transport for
   `daski_fetch_artifact`) and coordinated provider metadata + harness
   changes.
6. Release develop → main per the deploy runbook (this also finally ships
   `9789e06`), then re-run the daski-test suite twice: once healthy, once
   with the embedder forcibly degraded. Green bar = scenarios a, b, e2, e3
   pass in both modes; e1's document check passes; e4 completes without the
   paid-path retry roundtrip.

## 5. Non-goals

- Upgrading `@xenova/transformers` → `@huggingface/transformers` (v3) or
  changing the embedding model — orthogonal to the outage; revisit later.
- Weakening the provider's one-time/audience-bound document security model.
- Provider-side auto-refunds or retry semantics for screening holds
  (e4 verified the current discipline is correct).

## 6. Open questions

- Confirm the upstream 403 cause from gateway Railway logs (anonymous HF
  rate-limiting vs. something else). Doesn't change WS1's direction — the
  fix removes the dependency either way — but informs whether build-time
  fetch needs an HF token or self-hosted files.
- `daski_fetch_artifact` binary transport: inline base64 with a size cap vs.
  gateway-hosted short-lived re-download URL. Decide during WS4 design.
- Should `availableCategories` ship on every search response (payload is
  tiny) or only on zero-result/degraded responses? Default: zero-result +
  degraded only.
